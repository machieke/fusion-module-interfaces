# S03.2: append-only native remember and same-session readback

The controlled native MeTTaClaw loop now routes approved synthetic `remember`
commands through independently placed Embedding, AtomStorage and Search providers.
A later `query` in the same session discovers the new payload through the published
index and authoritative storage. The native parser, preprocessing, creation label,
query selection, promotion, STV defaults, uniqueness and presentation remain native.
This adds one append-only command boundary; it does not adopt mutable memory,
Relations, episode provenance, belief revision or promotion.

The authoritative final outcome is the [gate manifest](../../../evidence/s03_2/verification.json).
The [same-memory trace](../../../evidence/s03_2/same-memory-final.json),
[source manifest](../../../evidence/s03_2/source-state.json) and
[contract decisions](s03_2-contract-decisions.md) provide the supporting detail.

## What changed and who owns it

The fresh application profile is `controlled-native-loop/5`; its command profile
is `neoclaw-append-only-memory/1`. Historical application profiles `/1` through `/4`
retain their bindings. Populated old journals cannot be reinterpreted as `/5`.

| Boundary | Responsibility and durable owner |
|---|---|
| Native application | Accepted turn/position occurrence, one UUID, pre-embedding time sample, inputs/selections/deadline, captured vector, progress, read views and result handoff |
| Embedding | Original pinned E5 evaluation under `neoclaw-e5-memory-text/1`; separate memory encode/disclosure authority and durable evaluation reservations |
| AtomStorage / feed | Four independent immutable accepts: opaque intent binding, payload, vector, enrollment; original receipts and authoritative source positions |
| Search maintenance | One named generation per accepted maintenance identity, verified checkpoint, publication and truthful coverage |
| Local compatibility metadata | Immutable metadata views containing creation labels/default STVs; existing local promotion lookup; no payload or real-vector cache |
| Search / AtomStorage reads | Ranked refs and distances, then verified authoritative payload hydration, under each query's retained view |

The native `remember` and `createMemory` bodies remain source checked. Three seams
wrap the original creation-time sample, append-helper call and creation-link call.
The supported startup path is `integration.neoclaw.native_loop APPLICATION.json`,
not a patch installed only by the single-command demonstration. Placement is
trusted composition, with identical caller business code and no legacy fallback.

`MemoryEmbedding` reuses S03.1's captured-vector lifecycle with a distinct purpose
profile. The query profile, unprefixed native `string-safe`, model, normalization,
float32 semantics and Search numerical profile are unchanged. The native parser
turns a model-response NUL into literal `u0000`; parity compares the accepted native
argument. Raw accepted payload and transformed helper input are bound separately.

AtomStorage 1.2 adds optional `observe(Mutation)`, not a new requirement on historical
AtomStorage providers. An observation returns original acceptance and source position;
it performs no retry. The closed append route admits only the four record roles and
validation reads. The opaque binding record prevents changed meaning after partial
acceptance. The existing `vector_enrollment.enroll` issues the other three creates.
DeTTa still receives application-neutral bytes. No application reads another owner's
database, and no cross-owner transaction is introduced.

Search 3.1 adds named `build`/`published` maintenance and a separate read descriptor's
`ready(snapshot)` observation. One deterministic generation and owner journal bind
the original source, corpus, model, principal, key and deadline. Uncertain unpublished
Chroma contents can be rebuilt in that generation; a verified checkpoint can be
published. Existing publication is observed without another build. The selected
read provider must confirm the retained generation before native success or replay.
Historical Search 3.0 remains available with its original semantics.

## Visibility, partial states and replay

The application allocates a random UUID once in the occurrence-acceptance transaction.
It persists the time selected at the original native point before encoding. A retry
reuses both; an identical command in another turn or position gets a new UUID even
when its timestamp is equal. This deliberately strengthens legacy physical-call
identity, which originally allocated another UUID on every helper invocation.

| Observed state | What can be reported | What remains required |
|---|---|---|
| Accepted occurrence / captured vector | Stable intent; possibly no storage acceptance yet | Observe or create the immutable records |
| Payload/vector accepted, no enrollment receipt | Partial storage effects; downstream availability unconfirmed | Complete and observe validated enrollment |
| Enrollment accepted | Stored, source position known | Publish a covering Search generation |
| Search published | Indexed at the recorded source head | Confirm the selected reader and matching metadata |
| Metadata ready | Compatibility view prepared | Durably select the coherent application view |
| View selected | New queries can bind this view | Confirm creation link and capture native success |
| Success captured | Exact `REMEMBER-SUCCESS` retained | Existing next-context handoff, subject to current authority |

Missing receipts mean **not yet observed**, not proven absence. A failure retains
the recoverable occurrence and independent partial-state fields; it does not emit
unconditional native success. Unrelated new turns cannot bypass pending work.

New query occurrences bind the active view at acceptance. Earlier queries and
captured results retain their own snapshot and metadata seal. Deleting a retained
generation produces explicit unavailability; it never silently retargets the query.
No operator configuration is edited between `remember` and the later `query`.
The existing controlled-loop admission rule still rejects mixed-operation batches
before effects. Read-your-writes is exercised across successive accepted turns;
multiple same-operation commands in one turn retain separate position identities.

Application encode sends and provider evaluations retain their existing separate
three-attempt bounds. A write has 96 reserved port calls and three build sends;
the maintenance owner independently permits three physical build attempts. There
are at most 32 physical generation directories, including unfinished named work.
Lost replies consume reservations. Original deadlines are never renewed. After
expiry, already committed completion may be observed/disclosed; missing encoding,
storage, publication or metadata preparation is not manufactured. Physical E5
execution before capture is not claimed exactly once; after capture the vector is
reused without another encoder call.

The supported writer is one trusted application journal/corpus with the existing
exclusive session lock. This is not a multiwriter protocol, ingestion framework or
scheduler. Separate owner commits can leave orphaned immutable records or an unused
generation, which are honest partial states rather than an atomic rollback claim.

## Reproduction and measurement limits

Use Linux, uv, native compiler/build prerequisites, OpenSSL, bubblewrap/user namespaces
and `/usr/bin/time`. Retain or rebuild the pinned native runtime with
`scripts/build_s01.py`; use the existing pinned DeTTa build recipe and Cargo lock.
The exact dependency identities above are mandatory. The unchanged
`integration.neoclaw.memory_build` recipe prepares the provider SDK/model with hashed
locks/assets; `embedding_caller_build` prepares the separate E5-free caller.

```bash
export S01_RUNTIME="$PWD/artifacts/s01/native-02/runtime.json"
export S01_DETTA="$PWD/artifacts/m5/reproduction-01/providers/detta/target/debug/fusion-detta-adapter"
export M2_DETTA_BINARY="$S01_DETTA"
export PYTHONPATH="$PWD" PYTHONDONTWRITEBYTECODE=1 HF_HUB_OFFLINE=1
uv run --python 3.11 --locked python -m integration.neoclaw.embedding_caller_build \
  artifacts/s03_2/reproduction --helper artifacts/omega-mapping-source/petta_lib_chromadb/lib_chromadb.py
artifacts/s03/venv/bin/python -m integration.neoclaw.append_oracle \
  --prepare --corpus artifacts/s03_2/corpus.json --evidence artifacts/s03_2/original.json
artifacts/s03/venv/bin/python -m integration.neoclaw.append_run \
  --corpus artifacts/s03_2/corpus.json \
  --caller-runtime artifacts/s03_2/reproduction/caller-runtime.json \
  --evidence artifacts/s03_2/same-memory.json
S03_2_EVIDENCE="$PWD/artifacts/s03_2/tests" artifacts/s03/venv/bin/python -m unittest -v \
  tests.test_append_contracts integration.neoclaw.test_append
```

For a new provider target, run `integration.neoclaw.memory_build DIRECTORY` and set
`S03_RUNTIME`, `S03_SDK`, `S03_MODEL`, and `S03_HELPER` as in the [S03 runbook](s03.md#reproduction).
The executed reproduction builds a fresh caller target and fresh session journals;
it reuses verified native binaries, provider SDK and pinned model assets. Package
caches may be warm. It is not a fresh compiler/provider build or empty-global-cache
claim. Trusted `append_composition.configure` constructs the initial composition once.

[Measurements](../../../evidence/s03_2/measurements.json) record individual original
and adapted startup, total time, caller peak RSS and first-observed append stages.
These are single observations on this host, not throughput, quality or performance
improvement estimates. Caller RSS excludes separately running HTTPS providers.
Stage timestamps measure when the application observed progress, not owner commit
latency. Index publication and selected-reader readiness remain distinct.
Other correctness suites were active during the final comparison. Operator corpus/
index preparation and separate provider startup are outside the measured caller
interval; local descendants contribute to GNU time's process measurement. These
placements therefore do not constitute a controlled latency or memory benchmark.

and one build reservation. Exact original feedback, captured memory vector and
candidate ordering matched in all three placements. Source identities and random
UUIDs differ between independent runs; their correspondence is explicit in the trace.
Returned distances matched within the comparison's `1e-6` tolerance. This does not
promise stable ANN tie order or bitwise equality on other hardware.

unchanged. There are five adoption entries covering four native user commands;
the fifth is the composite append-only `remember` boundary, including its explicit
memory-purpose Embedding dependency. No whole family or whole Omega is promoted.

test rerun and chain execution are **NOT_RUN**. Same-host process restart assumes
intact journals. Existing ANN/tie and cross-hardware numerical limits remain.

not run; the required additional mixed placement was HTTPS encoder/local retrieval.
Required blocked prerequisites, executed failures and observation timeouts are
reported separately in the gate manifest. Stop at S03.2.
