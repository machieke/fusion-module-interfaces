## 0. Outcome: move from individually qualified services to useful agent workflows

The earlier A–N reference-distribution programme is complete. Reuse it. Do not repeat it as the main deliverable.

Deliver a developer preview in which an operator can install the distribution, start two actual native Omega agents with different identities, admit bounded synthetic tasks, use the advertised tools, share selected knowledge, inspect their provenance and work, and recover the interaction through the deployed interfaces.

The programme must add executable functionality beyond the reference distribution:

1. One capability-driven application composition instead of a new task-specific launcher for every scenario.
2. A real tool/skill catalogue, provider selection and installable contracts/client development kit.
3. Durable multi-session input, event history, episode navigation and working task context.
4. Native linking and unlinking through typed structural ownership.
5. Explicit experimental memory supersession and logical withdrawal, without falsely promising physical erasure.
6. Narrow sandboxed workspace file tools, not arbitrary shell execution.
7. Two genuine native agents exchanging work and discovering shared knowledge through services.
8. One combined native workflow using memory, evidence, priority, relations, context, messaging and recorded ModelInference.
9. A commitment of an actual approved artifact from that same agent workflow through the existing isolated chain interface.
10. Developer-facing observation, scenario evaluation, compatibility tests and a usable local operator interface.

**Do not end the assignment after preparing another live-generation approval request.** Live generation is optional, separately authorized verification; it is not a prerequisite for the engineering work in this programme.

The supported outcome is a **bounded synthetic-data developer preview**. It is not full adoption of every Omega capability, a production tenancy/security certification, a general autonomous agent, a multi-node deployment or a claim that reasoning executes on chain.

### Work continuously through the backlog

- Internal package gates are assertions, not new user-approval checkpoints.
- Make routine reversible decisions: code organization, small schemas, compatible adapters, test layout, resource sizing within existing constraints and implementation order.
- Inspect the actual workspace once and identify already completed requirements. Avoid repeating historical inventory and hash audits unrelated to changed code.
- Reuse the native engine, existing owners, contracts, profiles, campaign controls, charts, operator entrypoint and test infrastructure.
- Fix defects exposed by this scope, preserving the invariant each failing test protects. Do not stop at a diagnostic report when a safe in-scope correction is feasible.
- A blocked dependency does not stop independent packages. Missing live approval blocks only real generative-runtime activity, not development, recorded-backend tests, deterministic reasoning, E5 encoding or isolated chain tests.
- Keep one compact progress ledger and one final integrated report. Do not produce a new handoff proposal for work already in this assignment.
- If the session ends, checkpoint exact code, artifacts, unfinished tests, cluster resources and the next command. Resume this programme; do not call incomplete packages future scope.
- Completion is not measured by test count or the number of documents. Required native consumers must actually use the implemented interfaces.

## 2. The product slice and execution graph

The default deliverable has one agent/session owner per native agent and one active writer per shared provider journal. Two agent callers do **not** mean two writers opening the same database files. Shared service requests are authenticated, serialized and version-checked by the owning service.

The two-agent demonstration should use this shape:

```text
Operator / isolated IRC peer
      |
      v
Omega A: native loop, session state, tool admission
      |                       |
      | typed task/reference  | own authorised service calls
      v                       v
Messaging / AtomStorage  <-> shared scoped services
      |
      v
Omega B: native loop, separate session and credentials
      |
      +-> Embedding -> Search -> AtomStorage
      +-> EpisodicMemory / BeliefRevision / Attention / Relations
      +-> bounded named execution or synthetic workspace tools
      |
      +-> correlated result reference -> Omega A
                                             |
                                             +-> approved artifact inspection

```

Each positive networked record is explicitly synthetic and shareable for the selected recipients. Agent A and B also have separate synthetic private scopes used for denial tests. Their model backends are recorded fixtures unless separately authorized later.

## 4. P02 — implement the typed tool/skill catalogue

The historical mapping distinguishes provider Registry/Resolver from X05 ToolDescriptor. Implement that distinction instead of stuffing user-facing tool semantics into provider descriptors.

Each ToolDescriptor must identify at least:

- Stable tool ID, version/profile and compatible native vocabulary.
- Typed arguments and result/error shapes.
- Declared effects: read, local state mutation, shared state mutation, external observation or external send.
- Required provider interfaces/profiles and optional capabilities.
- Scope, disclosure purpose, input/output limits, timeout/budget policy and replay classification.
- Whether it is available to a model, an authenticated operator, an internal adapter or a fixture-only test driver.

Use the operator-controlled catalogue and existing resolver to select concrete providers. A new provider cannot register itself as trusted solely by announcing a name or descriptor. No open marketplace, consensus registry or new discovery infrastructure is required.

Generate the native `getSkills` presentation from the intersection of **implemented capabilities, successfully selected providers and current session authority**. Prompt help does not grant authority. The dispatch/admission path must validate the full command batch independently against that same selected schema/policy.

Retain exact allowlists for historical campaigns. The new developer profile may allow new bounded text inputs under an explicit synthetic session policy, rather than hard-coding one known query per scenario. It must not accept arbitrary code, URLs, paths, recipients or policy modifications.

Preserve native parsing. Add adapters at declared dispatch points; do not replace the MeTTaClaw loop with a Python imitation. If a new stable-handle syntax or command is needed, declare it as a new vocabulary/profile and test rejection under historical profiles.

Selection freezes interface, profile, implementation identity and policy revision for accepted work. Availability changes do not silently retarget an accepted operation. A new session can deliberately select another conformant implementation.

**Required tests:** unsupported commands, whole-batch rejection before any effect, expired/revoked capabilities, unavailable provider, fabricated principal, stale descriptor, unknown required schema fields, malicious text in descriptions and compatibility with prior fixed-tool profiles.

## 7. P05 — stable handles and scoped shared read views

- Give the native compatibility facade an explicit stable-handle form. Keep timestamp aliases only where they resolve unambiguously and under current authority.
- Reject missing, ambiguous, wrong-type or wrong-scope handles before effects. A display timestamp, nickname, content hash or UUID string is not an access capability.
- Return legitimate handles/receipts through typed results; tests may use them in later commands. Tests may not obtain the handle by querying private owner SQL and supplying it as an answer shortcut.

Add two-agent corpus membership to trusted configuration with separate principals and per-operation permissions. Start with one explicitly shared synthetic corpus and one private synthetic scope per agent. Unknown identity and an agent's arbitrary claimed role never imply membership.

For shared ingestion, service owners serialize their own commits and acceptance feeds. An agent's read view binds actual source coverage, generation, lifecycle/relations and applicable presentation snapshots. A late completion of an older Search build may not regress the active view to an older source head.

Existing accepted reads remain bound to their views, subject to current disclosure policy. New reads must explicitly select a ready view satisfying their coverage requirement. A lagging shared index is not a successful empty result.

## 9. P07 — typed native link and unlink adoption

The reference Relations provider currently supplies assertion, lookup and traversal. Extend its selected profile with **logical structural retraction** for new synthetic records, preserving historical assertion-only profiles.

For `link(memory, episode/event)`:

1. Resolve and authorize exact memory and C1 endpoints.
2. Create/reuse a verified immutable episode/event-handle atom where the structural port requires AtomRef endpoints; do not cast an EpisodeRef or timestamp into an AtomRef.
3. Assert a declared typed relation with named ordered roles and a stable operation identity.
4. Read the committed relation through the native presentation path.

For `unlink`, record an owner-controlled, idempotent retraction event referencing the exact asserted relation and expected state. Do not delete its historical payload or rewrite prior episode history. Current traversal excludes retracted relations; historical traversal requires an explicit authorized snapshot.

If native pair-based syntax matches several edges, refuse or use an explicitly declared unambiguous relation handle. Do not retract every vaguely matching edge. Re-link after a committed retraction is a new assertion occurrence under the declared state model, not an accidental replay of the original success.

Structural unlink does **not** retract a belief contribution, erase its provenance or reduce its weight. The assessment ledger can retain its actual evidence even when a presentation link is no longer active. Document that distinction in ToolDescriptor and output semantics.

Test same-key conflicts, duplicate assertion/retraction, retract-versus-traverse races, ordered roles, old pages, ambiguous aliases, foreign scope, interruption around payload and owner commits, and native query/episodes readback.

**Exit:** native link/unlink operate through Relations with truthful active/historical semantics; no direct Chroma metadata mutations or hidden C2 effects.

## 10. P08 — implement working task context rather than a no-op pin

The inspected native `pin` returns a success token without maintaining working-memory state. The new preview must implement actual behavior under an explicitly new application profile, while preserving the historical no-op behavior where that profile is selected.

Working task context belongs to the application, not AtomStorage truth, C1 evidence or Attention. Provide bounded pin/set, inspect and clear/unpin operations with durable identity and revision. Expose only the native vocabulary explicitly declared by the new catalogue.

Keep a small fixed maximum item count and total UTF-8 bytes. An intentional repeated action may create or replace a selected item according to its explicit ID; replay must not duplicate it. Capacity refusal is explicit and must not silently drop an acknowledged task item.

The next context includes the actual selected task items, their role as unverified notes and their immutable view identity. Already captured context retains its original selection; a new context may observe updated task state. Input pins are data, never executable definitions or authority to call tools.

Provide deterministic context allocation among system instructions, task context, history, current input, promoted memories and actual feedback. Do not silently rewrite historical character limits into token limits. When token counting is unavailable, report the actual byte/character bound and never claim exact model-token accounting.

A context that cannot fit required authorized content must fail with a useful typed reason or a documented deterministic omission policy. Omitted optional content and truncation boundaries are visible. Do not use a generative summarizer to solve the limit.

Test actual `getContext`, old/new view retention, clear/replay, malicious delimiter text, unavailable items, receipt identity and caller restart.

**Exit:** `pin` becomes a genuine bounded working-context tool, without inventing another cognitive module.

## 11. P09 — versioned memory lifecycle on fresh synthetic data

This package makes an explicit experimental product decision for the new developer profile. It does **not** claim compatibility with legacy physical deletion or authorize migration/erasure of existing data.

### 11.1 Owner and representation

Keep AtomStorage payloads immutable. Add/reuse a small logical memory-lifecycle facet owned by the storage/memory authoritative service, with one owner for:

- Stable logical memory identity and its immutable revisions.
- Active, superseded and withdrawn states.
- Compare-and-swap head, lifecycle events and replay receipts.

Do not put lifecycle authority in Search, the UI, every agent or a separate permissive cache. A narrow sibling owner/port within the storage service is acceptable if current AtomStorage semantics must remain closed. Catalogue it as a facet/extension, not a new historical family.

### 11.2 `update` means immutable supersession in this profile

An update binds the accepted occurrence, original logical head, exact new content and representation. Persist new immutable content/vector/enrollment first; commit the validated successor state with a stable key and CAS; prepare the corresponding Search/presentation view; report ready success only after that view is selectable.

A crash may leave an unselected immutable record, not an acknowledged head pointing to missing content. Retrying recovers the same successor, not another UUID/head. Two competing updates from the same head cannot both win silently.

Do not transfer epistemic authority to changed text. The successor gets the explicit default prior/unassessed state of its selected policy, no copied empirical weight, and initially zero priority unless a separate authorized adjustment is made. Preserve the old record, evidence, priority and links historically. Any copied structural association must be an explicit typed action, not an automatic assertion of evidential equivalence.

Use an explicit output such as `MEMORY-SUPERSEDED` with exact predecessor/successor and readiness, rather than claiming complete legacy `UPDATE-SUCCESS` semantics that include automatic promotion/metadata transfer.

### 11.3 `forget` means active-view withdrawal, not erasure

Record a logical withdrawal. New normal queries and global context must exclude the record once the selected ready visibility epoch covers the withdrawal. Old ciphertext, payloads, backups, provenance and recorded outputs are not physically erased.

Use a truthful result such as `WITHDRAWN_FROM_ACTIVE_VIEW`, including what remains accessible. Never claim GDPR erasure, secure deletion, inability to reconstruct data or erasure of information already sent externally.

Historical inspection requires an explicit history permission. Retained query captures are immutable, but releasing them still checks current policy; a normal active-mode disclosure cannot use an old view as a bypass for a withdrawn item. A refusal must not rewrite the old recorded result into different bytes.

### 11.4 Indexing and presentation

Lifecycle state has an authoritative sequence/feed. Rebuild derives active membership from authoritative payload/enrollment and lifecycle records. Do not query arbitrary top-k and silently discard withdrawn items while claiming unchanged active-corpus ranking or completeness. Use a generation/filter implementation that expresses the selected active set and test its semantics.

Keep pending storage, lifecycle commit, projection publication and app visibility separate. Do not return an older successful view when a request requires the new lifecycle epoch. Declared archived access and active retrieval are different operations/profiles.

Do not delete C1/C2 state as compensation for an interrupted update. No garbage collection, compaction or byte erasure is required. Finite append/retention caps may explicitly bound the preview.

**Required tests:** intentional semantic differences, old/new views, update/update CAS, update/withdraw race, duplicate replay, projection lag/rebuild, copied-evidence refusal, zero/retained priority, authorization and actual pod/process interruption.

**Exit:** new native memories have an explicit recoverable lifecycle, rather than a destructive legacy helper hidden behind an immutable interface.

## 12. P10 — narrow synthetic workspace file operations

Adopt the existing `read-file`, `write-file` and `append-file` vocabulary only for a new **bounded synthetic workspace profile**. Keep arbitrary shell and arbitrary filesystem access excluded.

The file provider owns a dedicated workspace and its mutation journal. Reuse named DelegatedExecution/authorization machinery where it fits; do not use AtomStorage as a pretend POSIX filesystem or offer `execute(command)`.

Specify fixed approved logical path roots/aliases, principal/scope/session, maximum files/bytes/line lengths, expected revisions and output limits. Root selection is operator-owned. Reject absolute host paths, traversal, symlinks, special files, hard-link escape and path-resolution races. Use directory-relative safe opens or equivalent confinement; checking a string prefix is insufficient.

Keep the provider separate from agent source, credentials, config, prompts, history, model assets, journals and mounted cluster credentials. Files cannot be imported/executed as code. Reading an arbitrary internet file is not included.

For write, stage a bounded desired version then atomically replace under owner control, preserving the exact accepted intent and receipt. For append, assign stable entry identity and revision so a lost response cannot append the same entry twice. Test uncertain interruption between file effect and journal receipt; detect/reconcile the exact intended resulting content instead of blindly repeating a write.

Do not claim cross-file transactions or arbitrary exactly-once external effects. Interrupted ambiguous state can remain explicitly unresolved if the supported profile cannot reconcile it.

Compare native positive formatting/content on admitted inputs, with intentional changes to safety, typed errors and replay. Actual native commands must exercise the provider and consume the result; tests may not write the target file outside the tool under test.

**Exit:** three narrowly admitted native file tools work behind a replaceable service without exposing host execution or private paths.

## 13. P11 — two actual native agents, not one agent and a renamed fixture

Deploy two native Omega application workloads, each with its own PVC, principal, session, capabilities and context. They may use the same image and shared service deployments, but cannot share application journals or impersonate one another.

The recorded model backend selects bounded command proposals. It must not be the task worker, retrieve a result from the evaluator or prewrite the shared answer. Both agents' loop, parser, tools, persistent state and result consumption must execute.

Implement the smallest typed task/result exchange through existing Messaging:

- Task occurrence and parent/correlation, sender and intended assignee.
- Allowlisted operation/workflow, permitted source scope, input/query or approved reference.
- Original absolute deadline and finite task/tool/relay budgets.
- Acceptance, execution status, result reference and explicit terminal/refusal state.
- At least one authenticated acknowledgment at the existing durable boundaries.

Use fixed operator-assigned roles for this preview. No task bidding, dynamic swarm formation, recursive delegation, shared arbitrary credentials or general distributed scheduler.

Required workflow:

1. Omega A actually remembers an approved new synthetic fact in the shared corpus.
2. After its ready source view is observable, A sends B a task to retrieve a fact by query. The task does not contain the answer reference or content.
3. B accepts through its real native input path, selects a sufficiently fresh authorized read view and performs actual query/hydration.
4. B returns an authorized result reference and source/view binding through Messaging.
5. A retrieves and validates that result through declared ports and uses it in its next native context/response.

Perform the converse role direction or a second independent task without rebuilding the deployment. Demonstrate a distinct equal-text request, duplicate delivery, wrong agent response, revoked shared membership and a reference unavailable to the recipient.

Record result provenance as agent B's observation/report. It is not independent corroboration merely because B repeats A's source. Scope permissions determine what each agent can see; an opaque ref must not bypass them.

For concurrent shared writes, keep one authoritative owner process but exercise requests from both callers.
